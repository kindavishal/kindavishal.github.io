TubeMonitor: vibe-coding internal tools as a non-engineer

May 2026 ~5 min read

In early 2026, Firecrawl's YouTube tracking was broken. Not completely — the existing third-party tool was logging data. But it was under-counting creators in our network by a meaningful margin, missing spillover views on untagged videos, and producing weekly reports that didn't answer the questions the team actually had.

I needed to either fix the tool or replace it. I replaced it. This is the build story.

The data problem

The third-party tool tracked what it was configured to track: direct referral links and tagged video URLs. What it missed was everything else — organic mentions, untagged tutorials, competitor comparisons that mentioned Firecrawl in passing, and audience spillover from creator social posts linking to untracked videos.

When I was reporting creator program results, I was systematically under-counting reach. That's a data integrity problem, not a dashboard problem. You can't fix it with a better chart; you need better data collection.

Why build instead of buy

I looked at other YouTube analytics platforms. The enterprise options were expensive and still wouldn't surface organic mentions without a custom feed. The lightweight options lacked the API depth to track across the creator network the way I needed.

The other factor: Firecrawl is a web scraping tool. I had API access to a scraper that could pull structured data from YouTube pages at scale. Buying a third-party YouTube analytics tool when Firecrawl is the product felt like buying a hammer while standing in a hardware store.

The build approach: orchestrating AI Studio

I'm not an engineer. I can read code well enough to understand what it's doing and debug output against expected behavior. I can't write production-grade systems from scratch. What I can do is scope a problem precisely, describe system architecture in enough detail that the spec is unambiguous, and hold the output to a standard.

That turned out to be exactly what building with Google AI Studio required. I treated it like a PM directs an engineering team: write the spec, review the output against requirements, identify failure modes specifically (not generically), and iterate.

The key discipline was in the spec. Every component started with a written description of: what data comes in, what the component does, what state it produces, and what failure looks like. When the generated code had bugs, I described the observed behavior versus the expected behavior — not the code — and asked for a fix. That constraint kept the iteration loops short.

The stack

TubeMonitor tech stack

  • Next.js — frontend dashboard, server-rendered for performance
  • Supabase — data storage and queries (Postgres, no separate backend to maintain)
  • Vercel — deployment with instant preview builds for testing iterations
  • Firecrawl — the data layer; pulls video metadata, view counts, and engagement signals

Stack choices were all made for the same reason: minimal setup, no infrastructure to maintain, and fast iteration cycles. Supabase gave me a Postgres database with a clean API and no backend layer to manage. Vercel gave me preview deploys so I could test changes against real data before shipping them. Firecrawl gave me the scraping primitives without building a crawler from scratch.

What TubeMonitor tracks

  • View performance — weekly and cumulative views across every creator in the ambassador network
  • Spillover — organic views from videos not formally tagged in the program (the metric the third-party tool missed entirely)
  • Engagement signals — comments, likes, and shares relative to view count as a proxy for content quality
  • Competitive share of voice — where Firecrawl appears relative to competitors on the same creator's channel

The share-of-voice module is the most strategically useful surface. It tells you not just how many views our content is getting, but whether a creator's audience is spending more time with our content or a competitor's — which is actually the question that matters for program investment decisions.

The app went from spec to deployed and in use across teams in one week. It replaced the third-party tool the same week it shipped. Marketing, partnerships, and the founders now use it for weekly reporting.

What worked and what didn't

What worked: writing the spec first. The most important hour of this build was the session where I listed every question the dashboard needed to answer before writing a single line of code. That list became the acceptance criteria for each component and the test suite for each iteration.

What worked: being specific about failures. When AI-generated code broke, the quality of the fix depended entirely on the quality of the bug description. "It's not working" produced bad fixes. "The view count for creator X shows 0 after the scrape cycle completes, but the Supabase table shows the correct row was inserted — the query is filtering on the wrong field" produced correct ones.

What didn't work: my first assumption about data freshness. I built the scrape cycle to run daily, which was too infrequent when monitoring active creator campaigns. During launch weeks I needed near-real-time data. I switched to on-demand scraping with a cache layer — scrape on request, serve from cache if data is less than two hours old.

The broader point

The gap between "operator who can describe a system" and "operator who can ship a working internal tool" used to be months of learning to code. It's now a few days of disciplined AI-orchestrated building — if you can write a precise spec and hold the output to a real standard.

That's a one-way door. Operators who figure this out early accumulate compounding leverage. Those who wait for engineering bandwidth don't.

I'm not a production engineer. I don't ship customer-facing code. But for internal tools — dashboards, data pipelines, reporting surfaces — the constraint is no longer technical skill. It's problem definition.
